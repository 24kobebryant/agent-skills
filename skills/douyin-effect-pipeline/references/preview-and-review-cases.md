# 预览、打包与审核案例

关键词：副屏、错误窗口、二维码失败、200M、图标上传、安全风险。
来源范围：2026-09 大米特效会话，像塑 9.3.2。历史事实供生成假设，不是当前平台根因结论。

## UI-001：切换主副屏仍点不到正确编辑器

- 已观察：父窗口与多个编辑器子进程共享应用身份；按应用名激活不足以选对工程。
- 排查：工程绝对路径 → 进程候选 → 对应加载日志 → 当前窗口 ID/边界/截图。进程没暴露路径则记 unknown，不能把全局最新日志强行绑定给它。
- 操作：优先可访问性元素；坐标回退必须使用当前窗口与截图缩放，副屏原点可能为负数。不要保存历史 PID/坐标作为下次命令。
- 验证：输入后读回目标字段；剪贴板或快捷键可能落在别的应用。必要时在可用工具支持下针对已确认 PID 输入。

## PREVIEW-001：“程序异常，二维码生成失败”

- 已观察：该文案下曾出现上传连接超时，而不是业务脚本崩溃；同包后来成功生成预览。
- 排查阶段：原生导出 → 包是否存在及指纹 → 上传连接/响应 → 服务生成预览码 → UI 展示二维码 → 手机扫码加载。每阶段独立标记，不重复盲点。
- 修复：依据当前日志定位；先排查当前连接和原生导出。非公开接口只是版本相关线索，不固化 Cookie 解密、签名猜测或一次性直连为通用工具。
- 验证：二维码有效载荷对应当前包；有二维码不等于手机效果通过。用户没扫码时如实记手机 not_run。
- 安全：日志可能夹带完整导出配置、base64 图标和凭据，只提取错误码、事件名、时间等安全字段。

## PACKAGE-001：源工程超过限额，清理后仍提示旧失败

- 已观察：调试视频/备份占了工程绝大部分；移出后源工程显著缩小，但已打开的提交页面曾保留旧上传失败。关闭并重新进入后重新上传才成功。
- 排查：用 `size` 分开统计磁盘、原生源工程包、效果包；限额以当前 UI 为准，不能混用。
- 修复：仅清理已确认不参与业务的目标。用户授权删除时按精确清单操作；不默认维护巨大备份。关闭重开表单是旧会话排障候选，不是所有失败的万能解法。
- 验证：新导出时间/包指纹、新上传事件、最终提交回执。素材引用和真实预览仍需检查。

## PUBLISH-001：图标有缩略图，却提示至少上传一个

- 事实：该 UI 状态在会话截图中出现；确切上传失败根因未确认。
- 排查：本地图标存在 → 尺寸/可读性 → 当前表单上传完成 → 字段校验通过。不能仅凭缩略图认定上传成功，也不能直接归因于图标画得不好。
- 验证：按手机小图尺寸审视主体/边缘；男女图标、名称、引导、前后摄像头均读回当前表单。提示必须符合真正触发机制，不用模糊文案掩盖跟踪失败。

## REVIEW-001：检测通过，审核说“安全风险”

- 已观察：原生技术检测通过、提交成功之后，平台仍可拒绝审核。两者是不同阶段。
- 未知：本次拒绝没有详细条款，不能确认具体原因。
- 推断：图标和效果展示硬物伸入真实鼻孔、反复掏动，可能引发危险模仿的内容判断；不得将此推断写成已确认规则。
- 排查：保留平台原文/效应 ID/时间，区分内容安全、技术安全和发布资料。静态脚本未发现网络或动态执行调用，不等于安全认证，更不解释内容审核。
- 修复边界：核查当时官方规则；若替代设计改变“伸入鼻孔”这一用户核心需求，先说明并取得选择。不能只改名称、临时藏掉画面或用审核版/上线版规避审查。
- 验证：保留提交记录并追加审核结果。技术通过不承诺审核通过；泛化拒绝原因不能靠重复提交验证。

## 如何追加本地知识（暂不做 RAG）

按症状复用或新增稳定案例 ID；记录适用版本、事实来源、未知项、排查步骤、修复边界和验证方法。不要追加完整聊天、凭据或巨型日志。新证据推翻旧结论时修改结论并保留日期，避免相互矛盾的重复条目。后续 RAG 可按案例 ID 分块，无需现在引入向量库。
